## 0b. Update: the resource model as the owner defines it

Stated by the owner after reading the first version of this review, and checked against the tree:

1. **The shipped parsers are cluster-scoped.** The kinds are `ClusterParser` (report parsers, output: findings), `SBOMParser` and `ClusterSBOMParser` (output: assets). The namespaced `Parser` (a tenant's own `mapping` parser) still exists in the tree. Whether it should go is **not decided**: removing it would take the tenants' own parsers away (see docs/35 B15). **F14 is fixed without removing it:** a tenant's `Parser` accepts only data runtimes (`mapping`, `declarative`).
2. **An SBOM is assets, not findings.** An SBOM parser produces components, edges and metadata (the inventory). It does not produce vulnerabilities: findings for SBOM components come only from the matcher or an external analyzer (docs/30, docs/32). The code does not follow this yet:
   - the host forces `opts.ExtractVulnerabilities = true` (`internal/sbom/parser.go:206`), against `extractVulnerabilities: false` in docs/32;
   - the CycloneDX module emits VDR vulnerabilities and the SPDX module emits a `vulnerability` event for every CPE (`sbom-parsers/wasm/sbom-*/parser.go`, option `extract_vulnerabilities`);
   - docs/30 section 6.1 allowed "optionally findings" in the `SBOMParser` output: that sentence is withdrawn.

   **F21 is replaced by:** remove the `vulnerability` event from the SBOM protocol, the option, the host handling (`internal/sbom/parser.go:245,362-390`) and the two modules; an SBOM upload yields no `RawFinding` at all. CycloneDX VDR and VEX statements are not lost by this: they belong to a VEX *report* parser (the `openvex` `ClusterParser`; add a CycloneDX VEX one if wanted), a decision for the owner. The constant-key problem of F21 disappears with the code.

   **F22 is restated:** Syft is an SBOM source, so it is an `SBOMParser` (`sbom-parsers/wasm/syft` exists). The `syft` `ClusterParser` with `category: sbom` (`internal/config/parsers/syft.yaml`, the Helm `ClusterParser`) must go; the 13 finding parsers in `parsers` already no longer contain it. "Is this an SBOM" is decided by the **resource kind** everywhere (gateway, processor, CLI, gate), not by a name containing "sbom" or by a category.
3. **Consequences for the pipeline** (to check, not yet verified in the code): an SBOM run must not go through the scan-finished and mass-close path of finding runs and has no scanner family of its own; the gate waits for the match job (docs/35 E5), not for findings; the upload response says that findings will follow from the matcher. docs/31 must list cyclonedx, spdx and syft under `SBOMParser`, not as `ClusterParser`s, and `dependencytrack` is gone from both.

## 1. What was reviewed and how

The working tree holds a large change that is not committed: 177 files changed, about 17,000 lines deleted (every Go parser under `internal/parsers`, all Dependency-Track code), and new work (WASM and Lua parser runtimes, `ClusterParser`, SBOM parsers, an in-process matcher, an external analyzer client, new CRDs, new web tabs) plus docs 29 to 33.

Method: three independent readers went through the code and the docs, each on one area (parsers and their runtimes; SBOM, analyzer and the Dependency-Track removal; the feeds spec against the feed code). They only read: **nothing was built, tested, vetted or run**, because the owner runs those and reports back. The most serious findings were then checked again directly in the code.

- **CONFIRMED** means traced in the code (by a reader, and for the ones marked "re-checked" also by a second look).
- **SUSPECTED** means it depends on something that could only be seen by running the code, a cluster or the network.
- Facts about outside systems were checked where a source could be reached: the OSV bucket list has no `GitHub` entry (so `GitHub/all.zip` in doc 33 does not exist; `GitHub Actions` is the only GitHub entry). The EUVD API page and the NVD developer page could not be loaded; those claims are marked unverified.

## 2. Verdict

The direction is sound and a lot of it is good: the WASM parsers are byte-identical to the Go parsers they replace (14 of 14 `parser.go` files differ by zero lines from the deleted ones, apart from the package line), the SBOM host protocol is a good design, the new CRDs are a sensible surface.

But as it stands:

1. **The tree does not compile** and CI would fail in four places (section 3).
2. **The shipped container cannot run any WASM parser or SBOM reader**: the modules are not in the image and nothing loads them from anywhere else (F8).
3. **Nothing matches components to vulnerabilities yet**, although docs 30 and 32 and several messages say it does (F21).
4. **Four Lua parsers silently drop every location**, so their finding keys change (F9).
5. **Two parsers can be mixed up**: a Bandit report can be taken for Semgrep and parsed to zero findings, which closes the real ones (F12).
6. Several documents say "Implemented", "all tests pass", "verified" for things that are not true of the tree (section 9).

None of these is a design dead end. Each has a fix below, ordered so that the tree is green first.
