# 28. QA report: end-to-end test on the dev cluster, 2026-11-17

This is the record of a test of Rampart as a user would run it: the deployed dev instance, the `rampart-demo-app`
pipeline (Semgrep, Gitleaks, TruffleHog, Trivy fs, config and image, Checkov, Syft SBOMs), Dependency-Track 5.2.1, the
operator, policies and the web UI. Every bug below was reproduced first, then fixed in the working tree with a test
that fails without the fix. **Nothing was committed or pushed, and nothing was deployed**: the dev instance still runs
image `a390e35`, so every bug in this report can still be seen there until the changes are built and rolled out.

Decisions made here are D103 to D111 in docs/16.

## 3. Found and not fixed

These need a decision, or were seen only in code, not at run time.

1. **`/api/v1/openapi.json` documents 35 of about 75 routes.** docs/11 says the spec is generated; D54 and D67 say it is a static file. The two do not agree, and the static file has drifted. A route table that generates both the mux and the spec would end this.
2. **`GET /applications/{id}/sbom/graph` is 404 for an application with more than one asset** (it looks at the wrong asset), and the error is `text/plain` with a body of a different shape than every other problem.
3. **A run made by a direct upload has no stored report** (`/runs/{id}/report` is 404), while a presigned upload keeps it. Decide whether direct uploads should store the raw report (D53 retention applies either way).
4. **Filter language**: `-owner:x` hides rows where the owner is NULL; `%` and `_` act as wildcards in `rule:`, `path:`, `purl:`, `asset:`; `severity:bogus` and `sort=bogus` are accepted and ignored; the full-text index `finding.search` is never filled, so free text is a sequential scan; `COUNT(*)` runs on every page.
5. **Track names are not bounded** (a 500-character track is accepted) and `track` unknown to the application becomes an ephemeral run, which is by design (D10) but is easy to hit by accident when testing.
6. **Bulk**: the same id twice counts twice; an unknown id counts as "matched".
7. **A tenant `RiskPolicy` replaces the cluster default completely** (see §5).
8. **`IdentityProvider`, `ClusterIdentityProvider`, `AccessBinding` and `ClusterAccessBinding` have CRDs but no controllers** (code review).
9. Code-review findings that were **not reproduced at run time**: webhook delivery recorded before it is handled (a retry after a transient failure is dropped); device-flow state in memory per replica; `rampart apply` with no database writes to memory and prints success; `TenantReconciler` ignores a lookup error and never unclaims namespaces; the target flag only gates three routes; `merge.go` holds a 1,900-line test store in non-test code. See docs/23 and the review notes of 2026-11-16.

## 4. The parser field contract

A finding is built from `domain.RawFinding`. What each producer fills:

| Field | Shown as | Built-in JSON parsers (Trivy, Grype, Snyk...) | SARIF | Mapping (declarative) |
|---|---|---|---|---|
| `RuleID`, `Title`, `Description` | rule, title, description | yes | yes (title now from the rule when the message is a record) | `ruleId`, `title`, `description` |
| `Severity`, `ToolSeverity` | severity, "it rated it" | yes | level and `security-severity` | `severity` + `severityMap` |
| `VulnIDs` | vulnerability id; links to feeds, KEV, EPSS, CVE page, impact | yes | **now**, when the rule id is a vulnerability id | `vulnIds` |
| `CWEs` | weakness | yes | rule tags | **now** `cwes` |
| `CVSSVector` | CVSS | yes | no (not in SARIF) | **now** `cvssVector` |
| `Location.Code` | file and line | yes | yes | `location.file`, `startLine` |
| `Location.Package` | affected component, fixed version, fingerprint | yes | **now** (Trivy message) | `location.package.*`, **now** `manifestPath`, `PurlBase` derived |
| `Category` | filter, compliance mapping | per parser | **now** by rule tags and id | package `category`, **now** per record `map.category` |
| `ToolRecordID` | occurrence key | yes | `guid` | `toolRecordId` |
| `RawPayload` | the evidence on the occurrence | yes | yes | the record |

Gaps that remain, and a recommendation:
- `remediation` and `confidence` are compiled by the mapping runtime and never read.
- There is no field for **references** or for free **extra fields** a tool has. Today they live only in the occurrence's raw record, where the UI does not read them. The feeds give the public links of a CVE, so this matters only for non-CVE findings (SAST, IaC). Recommendation: add `References []string` and `Properties map[string]string` to `RawFinding`, carried to the occurrence, and `map.references` / `map.properties` to the mapping spec.
- **There is no Lua.** Custom parsers are YAML with CEL (`runtime: mapping`); WebAssembly is planned for Phase 4 (D96, D98). A script runtime would need the same sandbox limits the CEL runtime has (cost cap, record cap, depth cap, no I/O); not recommended before Wasm.

## 5. Design decisions, evaluated

| Decision | Verdict | Why |
|---|---|---|
| **D10** The asset's application wins over what an upload names | Sound, was silent | Moving assets must be an admin act. The answer now says so (§2 #13). Consider an optional `strictApplication: true` on a token that makes a mismatch a 409 for CI |
| **D13** Mass-close guard (more than 50% and more than 20 findings) | Sound, proven | It held 3 closes on dev during the tests, with the run ending `completed_with_errors`. It did not stop bug #1 for small scopes (a scope of 1 to 20 findings closes without a hold). The format check (#1) is the real fix; the guard is the safety net |
| **D40, D41** `caps.kevDueDate: true`: the SLA is never later than the CISA due date | **Needs a change for non-federal use** | A new finding of Log4Shell (added 2021) is "overdue by 1788 days" on the day it is found, and shows red for ever. CISA's date is a deadline for federal agencies from the day it was added; for anyone else the useful rule is `min(CISA date, discovery + N days)` where N is the band's days. Suggest `kevDueDate: fromDiscovery` as the default and `exact` as the FedRAMP/BOD preset |
| **D41** `businessDays` and `startFrom: verified` refused by name | Sound | The CRD schema now refuses them at `kubectl apply`, with a clear message, before the operator sees them. Negative days are refused too |
| **D62** A tenant `RiskPolicy` replaces the default entirely | **Risky** | Applying a policy with one factor removed KEV, EPSS and exposure from every score of the tenant, silently. Suggest `extends: default` (add or override factors by name) |
| **D63** CEL for risk factors, checked at apply | Sound | A broken expression is `Ready=False InvalidSpec` with line and column, and the old policy stays |
| **D28/D40** Scores stored at ingest, no age factor | Sound, with a cost | Stored and explained scores can differ until a recompute. #11 shortens that to 30 s; consider recompute on write of the policy row |
| **D48, D90** Reads are tenant-wide; roles raise only | Open risk | A viewer reads every finding of the tenant. The CVE impact route follows the same rule. Decide before multi-team tenants |
| **D54, D67** No OpenAPI generator; static spec | Wrong in practice | The spec lists 35 of about 75 routes and the SPA types are hand-written, so the UI and the API drifted (inventory, vulnerabilities). Generate or test it |
| **D82** Connectors only as resources | Sound | `Connector` reconciles, checks the live connection and reports `Connected=True AuthOK` |
| **D92** DT: pull, `versions: latest` default | Was wrong | The default assumed DT flags the latest version. Fixed (#9). Keep the default, document `isLatest` |
| **D96, D98** Only the parser contract is public; trackers and sources later | Sound | Fewer promises. The mapping runtime needed the fields of §4 to be a real peer of the built-in parsers |
| **D35** No throughput figure promised | Sound | Not re-measured here |
| **D11** Fingerprint v1 | Sound, one trap | A parser that gives a name without a purl makes a weak fingerprint. The SARIF and mapping parsers now give a base purl |

## 9. Addendum: compliance per application, and the marks of the frameworks

Asked for after the test: show on each application what it meets today, and let a framework carry a logo.

**What it does**
- `GET /api/v1/applications/{id}/compliance`: every framework that reads the application, with the controls clear, open and not read, the open and accepted findings, and a verdict: `meets` (every control read, none open), `gaps` (a control has an open finding) or `partial` (nothing open, some control cannot be read). A framework with a `complianceScope` reads only the applications that list it; the others are named in `not_in_scope`, so the page can say why they are missing.
- The application page has a Compliance section: one row per framework with its mark, a sentence, and a bar with one stretch for clear controls and one for open ones. A row opens the Compliance page on that framework and that application (`/compliance?framework=&application=`, new search parameters). The Compliance page shows the mark and the name of the framework it reads.
- `spec.logoUrl` on `ComplianceFramework` and `ClusterComplianceFramework` (CRDs and Helm copy updated, validated at apply: `https`, at most 2048 characters, no credentials). `GET /api/v1/taxonomies/{id}/logo` serves it.

**Decision: the logo is read by the server, not by the browser.** The page's policy is `img-src 'self' data:`; opening it to other hosts would let a tenant's resource make every viewer's browser call a third party, and would show that viewer's address to it. The server fetches the address once (an SSRF-safe client: `https` only, no proxy, each connection and each redirect checked against private, loopback, link-local and metadata addresses, 3 redirects, 8 s, 256 KiB), checks what the bytes are (PNG, JPEG, WebP or a plain SVG; an SVG with a script, a handler, a foreign object, an entity or an external link is refused), keeps it a day (a failure ten minutes), and serves it with `nosniff` and a sandbox policy. The list tells the browser only the path on this server.

**Decision: no official logos are bundled.** I searched for the usage terms of each:
- **OWASP**: the logo files are released only after a signed trademark licence agreement, and the logo must not be altered ([OWASP mark usage guidelines](https://owasp.org/www-policy/operational/mark-usage-guidelines.html)).
- **ISO**: only ISO, its members and technical committees may use the ISO logo; others may not copy or modify it ([ISO, Can I use the ISO logo?](https://help.iso.org/en/articles/375997-can-i-use-the-iso-logo)).
- **PCI SSC**: its logos come through a separate download agreement, and no mark may imply "PCI compliant" ([PCI SSC brand style guide](https://www.pcisecuritystandards.org/brand-style-guide/)).
- **CWE**: the acronym and the logo are MITRE trademarks; the terms of use decide the rest ([CWE terms of use](https://cwe.mitre.org/about/termsofuse.html), not read in full).
- **NIST**: no general logo policy was found.

Showing a trademark in the product's own colours is an alteration, which the owners of two of them forbid. The built-in frameworks therefore get a mark of Rampart's own: one flat silhouette per family (disc, hexagon, square, octagon, arch) with the initials cut out, in the brand's indigo; a framework installed by the organisation is teal, with dark letters (white on teal is about 2:1). The colour carries meaning: indigo ships with Rampart, teal is yours. An organisation that has the right to use an official logo sets `logoUrl`. If the owners grant Rampart a licence, the files go in as assets and `logoUrl` is not needed.

**Tests**: `TestAPI_ApplicationCompliance` (verdicts, scope, the not-in-scope list, 400/404/401), `TestAPI_FrameworkLogoIsServedFromThisServer` (the address never reaches the browser; read once), `TestAPI_FrameworkLogoFailureIsAnErrorNotAHang`, `TestCheckLogo` (14 pictures and attacks), `TestFetchLogoSafely_RefusesWhatIsNotAPublicHTTPSAddress` (a real loopback server is not reached), `TestFrameworkSpec_LogoURL`; on the web side `frameworkMark.test.tsx`, `applications/compliance.test.tsx`. ## 10. Addendum: creating applications from an upload, branches and environments, SBOMs

**Can an upload name an application that does not exist?** Yes, as in the big tools, but on purpose. DefectDojo creates a Product only when the import carries `auto_create_context=True`, and the user needs the permission ([importing](https://documentation.defectdojo.com/integrations/importing)); Veracode's upload API creates an application profile when asked to ([upload and scan](https://docs.veracode.com/r/r_uploadandscan)); Snyk creates a project from `snyk monitor --project-name`, within the permissions of the organisation ([monitor](https://docs.snyk.io/snyk-cli/commands/monitor)). ArmorCode's behaviour is not in its public documentation, so it is not claimed here. Rampart created the application silently, so a typo (`rampart-demo-appp`) made an empty application. Now (D114): `createApplication=true` creates it (a maintainer, an admin or a CI token; a triager gets 403), `createApplication=false` answers 404 `application-not-found` and makes nothing, and without the parameter the old behaviour stays with a warning in the answer, so no pipeline breaks. The upload dialog offers "New application..." to a maintainer, shows the name it will be given, and sends `false` for an application picked from the list. The answer carries `applicationCreated`.

**Three branches, each a deployed environment: three applications?** No. An application is the product; a repository or image is an asset of it; a branch or environment is a **track** of that asset (D10). Findings are kept per track, a decision on a `not_affected` or `out_of_scope` finding follows the issue to the other tracks (D57), and the application's score reads them together. Three applications would split one product's risk, SLA and compliance into three, and a decision taken once would be taken three times. Make them three applications only when they are three different products (a service and its admin tool), not three copies of one.

What was wrong, and is fixed (D115): an SBOM was kept once per asset, so the three branches replaced one another and the inventory showed whichever ran last; and an SBOM of a pull request or a feature branch was saved although an ephemeral run must change nothing. Now an SBOM belongs to a track (migration 45); the inventory lists the newest SBOM of each track, with its track and application; the single SBOM of an asset (export, graph) is the primary track's (main, then default), not the last upload's; an ephemeral run saves none. `TestInventory_OneSBOMPerTrack_OnPostgreSQL`, `TestGatewaySBOM_AnEphemeralRunLeavesTheInventoryAlone` (fails without the fix), `inventory.test.tsx`.

**`trackedRefs`, which decides which branches count, is now built (D117).** docs/04 and D10 said a `ScanSource` lists `trackedRefs` and every other branch is ephemeral (it feeds the CI gate and changes nothing); the code passed no list, so only `main`, `master`, `default`, `release/*`, `prod` and `production` were tracked and a `develop` or `staging` branch never reached the inventory. Now:

```yaml
apiVersion: rampart.aspm.dev/v1alpha1
kind: ScanSource
metadata: {name: github-actions, namespace: acme}
spec:
  scannerFamily: semgrep
  trackedRefs: [main, develop, staging, "release/*", "hotfix-*"]
```

An entry is an exact name, a prefix ending in `*`, or `*` for every ref. The list **replaces** the defaults (list `main` too if you want it), a pull request (`refs/pull/`, `pull/`, `pr/`, `merge-requests/`) is ephemeral whatever is listed, and a source with no list keeps the defaults. The list is validated (at most 50 entries, no space or control character, `*` only at the end) by the CRD, by `rampart apply` and by the operator (`Ready=False InvalidTrackedRefs`; the last valid list stays in force). The same list decides the direct upload, the presigned upload and the `ephemeral` flag of the runs list. For the default source (an upload from the UI or with no `source`), name a ScanSource `default`. The match looks at the **branch** only; a run with an `environment` and no `branch` is tracked on the track named by the environment.

Found on the way and fixed: `SaveScanSource` kept the old policy whenever the new one was empty, so a policy or a `trackedRefs` list could be added to a resource but never taken out. The resource is now the source of truth (an absent policy means the defaults). Tests: `TestIsEphemeral_TrackedRefsOfASource` (16 cases), `TestDirectUpload_TrackedRefsOfTheSourceDecideWhatChangesTheInventory` (fails without the wiring), `TestApplyScanSource_TrackedRefs`, `TestScanSourceReconciler_TrackedRefs`, `TestValidateTrackedRefs`, `TestScanSourceTrackedRefs_OnPostgreSQL` (fails without the overwrite). The CRD is `deploy/crds/scansource.yaml` and its Helm copy: apply it with `kubectl apply` after the rollout, as for any CRD change.

**Why the same package appears twice with two assets** (the screenshot): the pipeline uploaded some SBOMs with no `repository` (the asset `default-repository`) and some with the repository URL. Send `repository`, `branch` or `environment`, and `commit` on every upload (the demo's `scripts/upload-to-rampart.sh` sends none of them), and the SBOM, the scans and the findings land on one asset.

**Schema version.** `CurrentExpectedSchemaVersion` and the chart's `minSchemaVersion` stayed at 42 through migrations 43 and 44; both are 45 now, and `TestSchemaVersionsFollowTheLatestMigration` keeps them in step.

**Verified on the new build (dev, image `b6cb4d9`)**: `hack/qa/live_smoke.py`, 32 checks, all pass: the format check, NUL, 413, export format, CVE record and impact, inventory, compliance per application, the Trivy SARIF details. ### Compared with the big products: is one application with a track per branch right?

| Product | How it models "one product, several branches" | Source |
|---|---|---|
| DefectDojo | One Product. Each import carries `branch_tag`, `commit_hash` and `build_id`, kept on the test and in its import history; `--reimport-condition branch` makes a reimport compare only with the same branch | [import-scan API](https://defectdojo-api-generated.readthedocs.io/en/latest/apimodels/ImportScanApi/), [dd-import](https://github.com/MaibornWolff/dd-import) |
| Snyk | One target (the repository); `--target-reference` (a branch or a version) groups the projects of one branch under it | [group projects by branch or version](https://docs.snyk.io/developer-tools/snyk-cli/scan-and-maintain-projects-using-the-cli/group-projects-by-branch-or-version-for-monitoring) |
| Dependency-Track | One project name; one **version** per branch or release (new SBOMs make new versions, not new projects), with `isLatest` (4.12+) and the known problem of version sprawl | [Jenkins plugin notes](https://plugins.jenkins.io/dependency-track/releases), [managing project versions](https://dependencytrack.github.io/docs/next/guides/user/managing-project-versions/) (community sources; not read in full) |

All three keep one product and mark the branch inside it, which is Rampart's application / asset / track. Rampart's Dependency-Track source does the same (`versions: all` makes the DT version the track). So three environments of one product are one application, not three. Where Rampart differs: those tools record **any** branch label, while Rampart records only the tracked refs and treats every other branch as ephemeral (D10), which keeps pull-request noise out of the inventory. That is a sound default only if the list of tracked refs can be set, and it cannot yet (`trackedRefs` is not built, see above). Until it is, a long-lived `develop` or `staging` branch is the one thing in this model that behaves worse than in the products above. Also not in Rampart: DefectDojo's per-import history of branch, commit and build (a run keeps its commit in its context, but there is no list of imports per branch).

The decisions that follow the same lines as the products: creating an application on purpose and by permission (D114: DefectDojo, Veracode, Snyk); a framework logo read by the server (D113); a finding's CVE described from the feeds and not from the report (D105).

## 11. Addendum: mapping a Dependency-Track project to an application

**Is the model right?** Compared with what the big products do, yes. Dependency-Track's own DefectDojo integration maps a project to a DefectDojo engagement by a **per-project property** ([DT docs](https://docs.dependencytrack.org/integrations/defectdojo/)), which is Rampart's rule 1; the proposal to auto-create the context is **opt-in and off by default**, with the order manual id, per-project override, then global default ([DT PR #5971](https://github.com/DependencyTrack/dependency-track/pull/5971), still open when read); and DefectDojo's connectors keep newly found items **unmapped until they are mapped**, by rule or by hand ([DefectDojo connectors](https://docs.defectdojo.com/en/share_your_findings/integrations)). Rampart's seven rules, an optional `defaultApplication` that is empty by default, and a list of unmapped projects are the same design. I found nothing public on how ArmorCode maps Dependency-Track projects.

**What was wrong was not the model but three gaps in it, and one thing in the configuration.**

1. **A project mapped by hand in the UI got no findings.** The mapping was stored and kept across syncs, but `SyncProject` took the application from the rules only, so a project no rule claimed stayed empty, and the portfolio sync did not schedule it. A person's mapping now comes first and bypasses the rules and the project filters (`versions: latest` included: someone who maps an older version wants it read). `TestSyncer_AProjectMappedByHandIsRead` (fails without the fix).
2. **The asset did not follow the mapping.** It was made once, under the application the mapping gave that day, and stayed there when a rule changed, the default was removed, or a person mapped the project. Unlike an upload (D10), the mapping is the declared truth for a Dependency-Track asset, so the asset and its findings now move. `TestSyncer_TheAssetFollowsTheMapping` (fails without the fix).
3. **A mapped project could not be seen or moved.** The page listed only the unmapped ones, and the map route accepted only those. `GET /api/v1/sources/{id}/projects` lists the others with the rule that put each there (`by_rule`, `mapping_rule`), the route accepts any project of the source, and the page has "Projects in an application" with "Change application". `TestDTrackAPI_AMappedProjectCanBeMappedAgain`, `TestDTrackAPI_MappedProjectsSayWhatPutThemThere`, `TestDTrackProjectMapping_OnPostgreSQL`, `dependencytrack.test.tsx`.
4. **Configuration, not code.** The dev `ScanSource` has `mapping.defaultApplication: rampart-demo-app`. Before the `isLatest` fix (§2 #9) it took no project, because none was flagged latest; after it, the default took the six other products (flare-reminders, calls-debug-dashboard, adl-backend and others) into the demo application. That is what the option is documented to do (docs/10 §3 rule 7), but on a Dependency-Track that serves several teams it is the wrong setting. Remove `defaultApplication` from that ScanSource (it is managed by Argo CD, so change it in Git), or add a property or a CEL rule per team, and use "Change application" for the six that are already in. Nothing was changed on the cluster.

Not done: a `defaultApplication` that is applied only to projects with a given tag or name pattern (the CEL rules already do that); a warning when a default takes more than N projects; the same "who put it here" column on the Applications page.

## 12. Addendum: what changed in an application, over a range of days

Asked for: for an application, which CVEs appeared and which were closed, over a range the person chooses.

**Does it exist in the big products?** Yes, in different forms. Snyk's Issues Summary has a date filter and drills down to the new and resolved issues of the range, with the key numbers compared with the previous period of the same length ([Snyk reports](https://docs.snyk.io/manage-risk/analytics/reports-tab/remediation-reports)). Tenable gives each finding a state (New, Active, Fixed, Resurfaced) and has a mitigation summary and a relative-date summary of what was discovered and what was remediated ([Tenable mitigation summary](https://www.tenable.com/tenable-io-reports/mitigation-summary)). DefectDojo's open-source dashboard has fixed seven-day tiles (created and closed), and its "opened" counts go by the date a finding was created, so a finding opened and closed in the range is still counted as opened ([DefectDojo dashboard](https://docs.defectdojo.com/metrics_reports/dashboards/introduction_dashboard/)). I found nothing on a per-application range view in Wiz or Orca.

**What was built (D119).** `GET /api/v1/applications/{id}/changes?from=YYYY-MM-DD&to=YYYY-MM-DD` (both days included, UTC; default the last 30 days; at most 366; a day that has not come is cut) returns the counts, the same counts for the range of equal length before it, one entry per day for the chart, and four lists of findings: **new** (first seen in the range), **closed** (closed in the range, with how: fixed, not affected, risk accepted...), **came back** (a `reactivated` event in the range, with when) and **open at the end** (worst first). Each list is cut at 1,000 and the answer names a cut list; the counts are exact. The application page has "What changed": a period list (7, 30, 90 days or two dates), a sentence with the comparison ("12 new (8 before), 9 closed (5 before), 1 came back. Open went from 40 to 43."), a chart with new findings above the line and closed ones below it, and the lists as tabs; each CVE opens the finding.

**Limits worth knowing.** "Open at the start" and "open at the end" are read from the finding as it is now: a finding that was closed and reopened lost its first closing (`resolved_at` is cleared), so the "came back" list (from events) is how a return is seen, and the open counts for a past date can be off by the findings that were reopened since. The list shows findings, not distinct CVEs: the same CVE on two assets is two rows.

**Does it affect the rest?** It adds one route and one section; no table, index or existing query changes. It reads one application's rows through the existing (tenant, application) index: 10,000 findings in the test answered in about 50 ms and 30,000 in 130 ms (`TestApplicationChanges_LargeApplication_OnPostgreSQL`, skipped with `-short`). If the call fails the section says so and the rest of the page renders (`changes.test.tsx`). Tests: `TestApplicationChanges_OnPostgreSQL` (new, closed, reopened, open at the end, the previous range, per day, tenant isolation), `TestAPI_ApplicationChanges` (range rules, defaults, 400/401/404/501, lists never null), `changes.test.tsx` (6 tests, axe).

## 13. Addendum: is "open finding = control not met" right? Compared with the standards and other products

**Finding.** No. Rampart marked a control "Not met" as soon as one open finding bore on it. The sources:

| Source | What it says |
|---|---|
| PCI DSS 6.3.3 | Critical patches within one month of release; other patches within a time the entity sets by its own risk ranking. A finding inside its window does not fail the requirement. |
| Vanta, Drata | An item is overdue only past its SLA; a missed SLA can be acknowledged with a reason. |
| CISA BOD 22-01 | A due date per KEV entry; binding on US federal agencies, a good reference for everyone else. |

**Fix (D120).** "Not met" only when a finding is past its deadline; open and still inside the deadline is "At risk" with the date. The finding page now lists its controls and the deadline, and the application page folds frameworks and can pin them.

**Differs from PCI DSS 6.3.3.** The clock starts at first sighting, not at patch release. Not fixed; see D120.

**Tests.** Go and SQL agreement on the same data, the at-risk status, `findingControls`, and web tests for the compliance page (at risk vs not met), the inspector section and the application pinning/folding.
